# ADR 0001: 客户模型采用"档案 + 地址簿"两层

**状态**：已接受
**日期**：2026-10-13

## 背景

设计客户信息表时，最初考虑用一个扁平表，每行 = 一个（客户, 收货人, 地址）组合。这种模型对应 Excel 现状，但隐藏了几个结构性问题。

## 决定

采用 `customers` 客户档案 + `customer_addresses` 收货地址簿的两层模型。

## 后果

### 正面

- **客户维度可聚合**。"满毅一共有几单""王总客户群共贡献多少营收"成为简单查询。
- **客户档案有挂载点**。未来加客户标签、来源、生日等属性都有归属。
- **数据完整性有约束**。`name` 唯一 + `customer_id` 外键，挡住录入错误。

### 负面

- **录入时多一步**。新建客户时既要建 `customers` 行，也要建 `customer_addresses` 行；应用层要么两步表单，要么事务封装。
- **跨表查询**。"列出满毅的所有地址"是 JOIN，应用层要理解这是 N 行结果。

### 风险

- `customer_addresses` 没有"每客户只有一个默认地址"的约束，本地自用暂不强制。
- `name` 区分大小写，未来同人大小写撞名需走合并流程。

## 替代方案

### A. 单表扁平模型

- 每行 = (客户名, 收件人, 电话, 地址)
- 拒绝理由：失去"客户档案"概念；重复建档无约束；对账/聚合困难。

### B. 三层模型（客户 → 收货人 → 地址）

- 引入 `recipients` + `addresses` + 关联表
- 拒绝理由：本地 10 客户、20 地址的体量下纯属过度设计；每次维护跨 4 张表。

## 备注

未来如果出现"同一地址被多个客户共用"（如店铺代收点）的复杂场景，再把 `customer_addresses` 拆为 `recipients` + `addresses` 多对多。当前阶段不值得。
